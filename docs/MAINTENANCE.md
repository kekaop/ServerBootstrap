# Замена миров на хостинге без внешних программ

`apply.mode: maintenance` заменяет **целые каталоги миров** через служебный мир и два перезапуска. Нужны только сервер, ServerBootstrap и возможность изменить `level-name` в server.properties. Плагин не запускает shell, отдельную Java или restart-script.

## Настройка

Пример: [examples/maintenance.yml](../examples/maintenance.yml). Замените URL и SHA-256 значениями вашего ZIP, добавьте профиль в `plugins/ServerBootstrap/config.yml`, перезапустите сервер.

```yaml
config-version: 1
profiles:
  lobby:
    source:
      type: https
      url: https://example.org/lobby-worlds-v1.zip
    version: "v1"
    sha256: "ЗАМЕНИТЕ_НА_64_HEX_СИМВОЛА"
    archive-root: "."
    apply:
      mode: maintenance
      worlds: [world, world_nether, world_the_end]
      include: [world, world_nether, world_the_end]
      required-files: [world/level.dat, world_nether/level.dat, world_the_end/level.dat]
    restart: true
```

Это пример традиционной структуры Bukkit/Paper до 26.1. Указывайте **реальные каталоги вашего ядра**. [Paper 26.1+ изменил расположение измерений](https://papermc.io/news/26-1/): для снимка с измерениями внутри главного мира используйте `worlds: [world]`, `include: [world]`, `required-files: [world/level.dat]`. Не добавляйте отсутствующие старые `_nether`/`_the_end`. ServerBootstrap не переносит измерения между форматами и не проверяет совместимость NBT с ядром.

Каждый указанный мир должен содержать `level.dat`. Делайте ZIP со снимка остановленного сервера той же версии/формата. Включайте все необходимые чанки, сущности, POI, datapacks, playerdata, advancements, stats и прочие данные. UID и данные игроков берутся из снимка; пользовательские изменения, отсутствующие в нём, останутся только в резервной копии. Корневой `session.lock` каждого мира исключается из нового каталога — ядро создаст свой.

Maintenance устанавливает только миры; `include` должен точно совпадать со списком `worlds`. Для плагинов и конфигураций предусмотрен direct. Узел по-прежнему привязан к одному имени профиля: при смене режима сохраняйте это имя. Изменение имени требует отдельной миграции узла.

## Порядок работы

1. Сделайте внешнюю резервную копию и выведите игроков. Отключите автозагрузку рабочих миров сторонними плагинами на время обслуживания. Выполните `serverbootstrap check lobby`, затем `setup-server lobby`.
2. Плагин скачает ZIP, проверит SHA/CRC/пути, подготовит копии миров и отдельный SHA-манифест. Рабочие миры пока остаются прежними, установленная версия не меняется. Сохраняется `WAITING_FOR_MAINTENANCE`, а `level-name` переключается на уникальный `sb_maintenance_<id>`.
3. **Первый перезапуск.** Ядро читает метаданные служебного мира. В onLoad плагин подтверждает, что его `session.lock` удерживает именно текущая JVM, а все заменяемые миры свободны. Затем прежние каталоги перемещаются в backup, новые — на их места. Версия/привязка фиксируется в этой же транзакции.
4. Плагин возвращает исходный `level-name`, сохраняет `WAITING_FOR_RETURN` и останавливает сервер. Игроки на служебный запуск не допускаются.
5. **Второй перезапуск.** Ядро читает новые рабочие миры. Плагин проверяет возврат, сохраняет результат в журнале операции и снимает обслуживание. Проверьте `serverbootstrap current` и содержимое мира.

При `restart: true` плагин использует только `Bukkit.shutdown()`. Повторный запуск делает автостарт хостинга либо администратор кнопкой **Start** в панели. Автостарт после штатной остановки есть не на каждом хостинге. При `restart: false` плагин ждёт ручного перезапуска на обеих стадиях; вход игроков и новые установки всё это время заблокированы. Даже при false для замены мира нужны оба перезапуска.

ZIP/staging/backup требуют свободного места. Распаковка и подготовка выполняются в рабочем потоке; перенос каталогов и восстановление — синхронно на служебном запуске до допуска игроков. После начала замены прерывать запуск нельзя без последующего восстановления.

## Ошибки и команды восстановления

Команды доступны в консоли хостинга; permission для прочих отправителей — `serverbootstrap.admin`.

| Команда/фаза | Поведение |
|---|---|
| `serverbootstrap maintenance-status` | Состояние, исходное/служебное имя мира, сообщение об ошибке |
| `MAINTENANCE_FAILED` | Вход закрыт; автоматического повтора/остановки по кругу нет |
| `serverbootstrap maintenance-retry` | Подготовить следующий запуск со служебным миром для отката/повтора; после commit — только возврат на рабочий мир |
| `serverbootstrap maintenance-cancel` | Отменить неподтверждённую установку; после частичного применения сначала нужен служебный запуск для отката |
| `WAITING_FOR_RETURN` | Файлы уже применены или отмена завершена; нужен запуск с исходным миром |

Команды retry/cancel не заменяют миры во время работающего сервера. При `restart: true` они запрашивают остановку; при false перезапустите вручную. После commit отмена запрещена: используйте retry для возврата. Применение старого снимка после успешной установки — отдельная установка с собственным backup.

Если хостинг задаёт имя мира аргументом запуска, переписывает server.properties или использует внешний world-container, подтверждение служебного мира не пройдёт: рабочие каталоги не будут затронуты. Исправьте настройки хостинга либо отмените операцию. `level-name` должен указывать на непосредственный подкаталог корня сервера. Файловая система должна поддерживать session.lock и атомарное перемещение каталогов в пределах одного тома.

Если другой плагин уже загрузил рабочий мир, замена запрещается. Отключите его автозагрузку, затем повторите. ServerBootstrap не изолирует каталоги от сторонних потоков/плагинов, игнорирующих session.lock. `/reload`, отключение/включение ServerBootstrap без остановки JVM и запуск двух серверов в одном каталоге не поддерживаются.

На служебном запуске HTTP listener не открывается, установка других профилей недоступна, команды восстановления работают даже при изменённом/невалидном config.yml. Для незавершённой direct-транзакции используйте offline recover; её нельзя безопасно восстанавливать при обычном onLoad.

## Сохранённые данные

- `plugins/ServerBootstrap/maintenance.properties` — указатель текущей операции и стадии переключения. Не удаляйте и не редактируйте его вручную.
- `transactions/<id>/prepared-worlds/` — подготовленные снимки, `maintenance-manifest.properties` — их SHA-256.
- `transactions/<id>/world-attempt-<id>/` — plan/phase/rollback.properties, прежнее состояние узла и `backup/0`, `backup/1`… с целыми старыми мирами. Соответствие номера имени — в plan.properties.
- `transactions/<id>/maintenance-result.properties` — итог успешного возврата или отмены.

Сбой между переименованиями восстанавливается по журналу на следующем **подтверждённом служебном** запуске. Неполный откат сохраняет backup и список проблемных миров; исправьте место/права/блокировки и выполните retry или cancel. Не удаляйте файлы, чтобы искусственно обойти ошибку.

Старые миры, завершённые журналы и `sb_maintenance_*` не удаляются автоматически. После подтверждённого возврата, проверки backup и остановки сервера их можно архивировать/убрать вручную. Не удаляйте исходный рабочий мир или каталог незавершённой операции.

Обычный Bukkit `onLoad` выполняется уже после чтения метаданных главного мира; именно поэтому нужен служебный запуск. Порядок виден в [Main.java Paper](https://github.com/PaperMC/Paper/blob/ver/1.21.11/paper-server/patches/sources/net/minecraft/server/Main.java.patch) и [DedicatedServer.java Paper](https://github.com/PaperMC/Paper/blob/ver/1.21.11/paper-server/patches/sources/net/minecraft/server/dedicated/DedicatedServer.java.patch). Проверка блокировок учитывает [особенности FileLock](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/nio/channels/FileLock.html): закрытие дополнительного канала на некоторых ОС снимает чужую блокировку той же JVM, поэтому такие каналы сохраняются до освобождения блокировки/завершения процесса.
